2 · Architecture: sync-to-Postgres, never live-proxy

Every page runs relational SQL across six joined tables (signals × companies × events × goals × snapshots). Proxying the API per pageview would burn credits on each click and force a rewrite of the whole data layer. So a script fills the same database and the query layer stays untouched.

4 · What the API actually returned

Docs describe endpoints; the wire format is where integration breaks. Each row below was confirmed against a live response before any code depended on it.

Three traps: the .JK suffix must be stripped; market cap is full IDR (schema wants billions → ÷1e9); the window clamps to 90 days.
/companies/1

Billing is asymmetric — design around it

2xx and 404 consume credits; 400, 401/403, 429 and 5xx are free. Empty result sets return 200, not an error. So a malformed query costs nothing, but a valid request for a symbol that doesn't exist still bills.

5 · How a sync run behaves

  1. Resolve the universe — curated (default) reuses the 34 companies already in the database; all pages the full screener and inserts newcomers.
  2. Pull prices — first run replaces the synthetic series with a trailing 90-day window; later runs request only trading days after sync_state.last_trading_date. npm run db:sync
  3. Backfill gaps — any ticker left with zero rows (from an earlier rate-limited run) is automatically re-pulled with a full window instead of being skipped forever.
  4. Refresh fundamentals — only for companies missing a row by default; --full forces all of them. npm run db:sync -- --full # +3 credits per company
  5. Recompute derived data (0 credits) — snapshots and market-intel scores are recalculated locally using the exact same formulas as seed.ts, so live and demo data score identically.
  6. Persist state — sync_state is written even when a later stage fails, so a crash never causes the next run to re-burn the full window.

1 credit × 34 tickers. Fundamental refresh stays off the daily path.

6 · Six bugs, and what they taught us

01  Empty string beat a valid fallback

DIRECT_URL= is not nullish, so DIRECT_URL ?? DATABASE_URL returned the empty string and Drizzle refused to connect. Fixed by treating blanks as unset.

02  Rate limiting ate a third of the sync

Nine tickers hit 429. Per-request retries at 750 ms were far too aggressive against the plan limit — added a global pacer, 429-specific 5→10→20 s backoff, and cut concurrency from 5 to 3.

03  Suspended stocks produced NaN

A halted name returns a constant close with zero volume, so the volume ratio became 0/0 = NaN — which poisoned the score and aborted the whole derived stage.

04  A crash re-burnt every credit

Sync state was saved only on the success path. One failure meant the next run re-pulled the whole 90-day window. State is now persisted on every partial-failure path.

05  Failed tickers stayed empty forever

Incremental pulls start at lastTradingDate + 1, so a ticker missed by a 429 never recovered. Now zero-row tickers get a full-window backfill.

06  Redundant work in the hot loop

The intel stage computed the score twice and re-read the snapshot it had just written. Refactored to carry values in a map — one query fewer per company.

The one-line fix that mattered most

Before — suspended name
// 0 / 0 → NaN
const volRatio = +(recent / base).toFixed(2);
After — neutral fallback
// base 0 ⇒ no trading ⇒ neutral 1.0
const volRatio =
  base > 0 && Number.isFinite(recent / base)
    ? +(recent / base).toFixed(2) : 1;

# Supabase production
DATABASE_URL=                     # POOLED  :6543 (pgbouncer) — app runtime
DIRECT_URL=                       # DIRECT :5432 — migrations only
The pooled connection is not optional

Serverless instances exhaust direct Postgres connections. Point DATABASE_URL at the pooled string, but keep DIRECT_URL on the direct one — Drizzle's schema introspection breaks behind pgbouncer in transaction mode.
