# Market Intelligence Methodology

## 70% — Sectors-Derived Market Layer

The market layer currently includes:

### Price Dislocation

Measures the magnitude of price repricing from the trailing high.

### Volume Anomaly

Measures trading activity relative to its baseline.

### Relative Performance

Measures company performance relative to its sector.

### Fundamental Context

Uses reported business fundamentals including:

- revenue growth
- EPS growth
- dividend yield

### Market / Industry Context

Adds surrounding:

- sector performance
- broader market performance

The result is a market-derived context that is more informative than a single price number.

---

# 20% — Business Evidence Layer

Business evidence contributes:

### Business Event

Whether a relevant company event exists and how mature the event is.

### Source Quality

Source quality contributes according to evidence tier.

### Event Materiality

Materiality considers whether the event contains economically significant information such as investment or project scale.

The purpose is to distinguish:

```text
MARKET MOVEMENT
```

from

```text
MARKET MOVEMENT
+
REAL-WORLD COMPANY EVENT
```

---

# 10% — SDG / 2030 Layer

The SDG / 2030 layer currently contributes:

### SDG Target Relevance

How strongly the business event maps to the associated SDG evidence.

### Execution Timing

How relevant the execution timeline is to the 2030 horizon.

This creates a structured relationship between:

GLOBAL PRIORITY

# Data Integrity

The application is designed to keep market data synchronization separate from browser requests.

The Sectors API key is used server-side.

The API key is not placed in a browser request path.

The application synchronizes market data into PostgreSQL and serves page queries from the database rather than exposing the Sectors API directly to the browser.

This architecture provides:

- controlled API usage
- persistent market history
- incremental synchronization
- local derivation of scores
- reduced client-side exposure
- predictable application performance

---

# Live Data

IDX Sectors 2030 runs on live data from the Sectors Financial API v2.

The deployment synchronizes real market data — prices, market data, index data, fundamentals, and optional foreign flow — into PostgreSQL, and all scores are derived from that stored data.

The footer badge shows the live sync status (last sync date, tickers synced, data coverage) and the remaining lifetime credit budget.

# Incremental Data Synchronization

The sync layer is designed to avoid unnecessary API consumption.

On the first synchronization, market data can be populated for the configured watchlist.

Later synchronizations are incremental.

The synchronization process tracks state and can refresh only data that needs updating.

This supports a more controlled API usage model.

---

# Credit Awareness

The Sectors integration tracks credit consumption for different data operations.

The synchronization process includes:

- a lifetime budget
- per-run guards
- source-specific credit accounting
- API pacing
- retry handling
- incremental refresh
- optional full refresh
- optional foreign flow refresh

This is intended to make the application operationally predictable rather than relying on uncontrolled API calls.

# Environment Variables

| Variable | Required | Purpose |
|---|---|---|
| `DATABASE_URL` | Yes | Runtime PostgreSQL connection |
| `DIRECT_URL` | For migrations | Direct database connection for schema operations |
| `SECTORS_API_KEY` | For live data | Sectors Financial API credential |
| `SECTORS_API_BASE_URL` | No | Sectors API base URL |
| `SECTORS_UNIVERSE` | No | `curated` or `all` |
| `SECTORS_DAILY_CREDIT_BUDGET` | No | Soft per-run guard |
| `SECTORS_MIN_INTERVAL_MS` | No | Global API pacing floor |
| `SECTORS_INDEX_CODE` | No | Index used by the time-cycle module |
| `SECTORS_INDEX_HISTORY_DAYS` | No | Stored index history depth |
| `SEGMENTS_API_KEY` | Reserved | Future labeling pipeline |
| `SUPABASE_*` | Deployment-dependent | Supabase connection settings |

An empty `DIRECT_URL` should not be left in the environment because it can override the runtime connection configuration and break Drizzle database operations.

- index history chunking
- foreign-flow response normalization

The API key is used only by the server-side synchronization layer.

# Database Architecture

IDX Sectors 2030 uses PostgreSQL as the persistent analytical store.

The database contains relational data representing areas such as:

- companies
- market prices
- market snapshots
- fundamentals
- business events
- SDG goals
- SDG targets
- event-to-SDG mappings
- signals
- market intelligence scores
- index prices
- foreign flow
- synchronization state

This allows derived research intelligence to be computed from stored market and event data.

---

# Why Store Data Instead of Proxying the API?

The application does not use the browser as a direct proxy to Sectors.

Instead:

```text
Sectors API
   ↓
Server-side synchronization
   ↓
PostgreSQL
   ↓
Derived calculations
   ↓
Application queries
   ↓
Browser
```

This provides:

- persistent historical context
- deterministic application queries
- reusable derived calculations
- controlled API usage
- better separation of secrets
- more predictable runtime behaviour

# Development Philosophy

IDX Sectors 2030 is designed around several principles.

## 1. Evidence before conclusion

Signals should be explainable.

## 2. Global relevance before ticker selection

The research question can begin with what matters globally.

## 3. Execution before claims

SDG alignment is not treated as proof of execution.

## 4. Market context before market conclusion

Price movement is interpreted within sector and market conditions.

## 5. Derived intelligence instead of raw-data display

The application should produce analytical outputs that are useful for research.

## 6. Time matters

Business execution exists within a finite horizon.

## 7. Research over prediction

The product helps researchers prioritize investigation rather than promise future returns.
